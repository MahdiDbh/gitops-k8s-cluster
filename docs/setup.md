# Setup — k3s, kubectl, Helm

This document describes the installation of the tools required for the
cluster, as performed on the development environment (Kali Linux, x86_64).

## Prerequisites

- A user with `sudo` access
- `curl`
- `systemd` (to manage k3s as a service)

## 1. Installing k3s

k3s is a lightweight Kubernetes distribution (single binary, embedded
SQLite database by default), well suited for dev/lab environments.

```bash
curl -sfL https://get.k3s.io | sh -
```

This command installs k3s in server mode (control-plane) and registers it
as a systemd service (`k3s.service`).

### Start / enable the service

```bash
sudo systemctl enable --now k3s
```

### Check the status

```bash
systemctl status k3s
```

## 2. Configuring kubectl

k3s ships its own `kubectl`, but here we use the standard `kubectl`
binary, configured via the kubeconfig generated by k3s.

```bash
mkdir -p ~/.kube
sudo cp /etc/rancher/k3s/k3s.yaml ~/.kube/config
sudo chown $(id -u):$(id -g) ~/.kube/config
```

By default `kubectl` reads `~/.kube/config`. To use a different path:

```bash
export KUBECONFIG=~/.kube/config
```

(add this to `~/.bashrc` to make it permanent)

### Verification

```bash
kubectl get nodes -o wide
```

Expected result: one `Ready` node with the `control-plane` role.

## 3. Installing Helm

Helm is the Kubernetes package manager, used here to install ArgoCD
(optional — we use the official manifest instead) and, most importantly,
`kube-prometheus-stack`.

```bash
curl -fsSL https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash
```

### Verification

```bash
helm version
```

## Verification summary

| Command | Expected result |
|---|---|
| `systemctl is-active k3s` | `active` |
| `kubectl get nodes` | 1 `Ready` node |
| `helm version` | Helm version printed |

## Alerting — Alertmanager → Discord

The alert routing configuration for Discord lives in
[`monitoring/alertmanager-config.yaml`](../monitoring/alertmanager-config.yaml).
This file **never** contains the real webhook URL: it is stored in a
Kubernetes Secret, created manually once per environment:

```bash
kubectl create secret generic alertmanager-discord-webhook \
  --namespace monitoring \
  --from-literal=webhookURL='<DISCORD_WEBHOOK_URL>'
```

Then apply the config:

```bash
kubectl apply -f monitoring/alertmanager-config.yaml
```

### Creating a Discord webhook

1. In Discord: Server Settings → Integrations → Webhooks → New Webhook
2. Pick the target channel, copy the webhook URL
3. Use it in the `kubectl create secret` command above

### Verifying it works

Trigger a test alert via the Alertmanager API (from the pod):

```bash
kubectl exec -n monitoring alertmanager-kube-prometheus-stack-alertmanager-0 \
  -c alertmanager -- wget -qO- --post-data='[{"labels":{"alertname":"Test","namespace":"monitoring","severity":"warning"},"annotations":{"summary":"Test","description":"Test"}}]' \
  --header='Content-Type: application/json' http://localhost:9093/api/v2/alerts
```

The message should appear in the configured Discord channel after
`groupWait` (30s by default).
